# Changelog

## Unreleased

- UTF-16 and UTF-32 files can be read and patched: `read` (byte and line mode) and `apply_patch` no longer refuse them as `binary_file` when `encoding` names that codec (`utf-16`, `utf-16-le`, `utf-32`, ...). Their text holds NUL bytes, which the binary check used to catch whatever the encoding (so the 1.9.0 note that line-mode `read` and `apply_patch` reject them no longer holds). Read with another encoding, such a file still fails as `binary_file`, now with a hint naming the codec to pass (`replace_text` and `multi_edit` give it too, instead of a raw `UnicodeDecodeError`).
- Byte-mode `read` with a UTF-16/32 `encoding` counts whole code units: `max_bytes` is rounded down to a multiple of 2 (UTF-16) or 4 (UTF-32), and an `offset` that is not one fails with `invalid_arguments`, so pages decode right from any page boundary. A surrogate pair cut by a page still shows as U+FFFD, like a UTF-8 character cut by `max_bytes`. With plain `utf-16`/`utf-32`, a read past the start decodes in the byte order the file's mark names.
- **Behaviour change:** with plain `utf-16`/`utf-32`, edits (`write` of an existing file, `replace_text`, `multi_edit`, `apply_patch`) keep the file's byte order mark as it was: a big-endian file stays big-endian and a file without a mark gets none. They used to rewrite it little-endian with a fresh mark, so git showed every line as changed. New files, empty files, and files converted from another encoding get one little-endian mark, also when the content starts with U+FEFF (it used to get two).
- An unknown `encoding` fails with `invalid_arguments` (`Unknown encoding: ...`) in `read`, `write`, `replace_text`, `multi_edit`, and `apply_patch` (also one that creates a file), instead of a raw `LookupError`. An edit with the right wide `encoding` of a file that does not decode (a lone surrogate, say) says the file is not valid in that encoding instead of a raw `UnicodeDecodeError`.

## 1.10.0

- Large output no longer breaks the host relay (Quick rejects results over roughly 300 KB). `execute` returns at most `max_inline_output_bytes` (default 30000) of head and tail per stream and saves the output (up to `max_capture_bytes`, head and tail) to a log, given as `stdout_path`/`stderr_path`. Any tool result over `max_result_bytes` (default 200000) is saved as indented JSON and replaced by a cut-down reply with `result_path` (shape below). Saved files go to `spill_dir` (default: a per-config folder under `%TEMP%\localforge-results`), which is added to the read roots so `filesystem read` and `search` work on them. Saved files are named `lf-*`; only those are pruned (newest 100 kept), so other files in the folder are never touched. A relative `spill_dir` resolves against `workspace_root` and environment variables expand; an unusable folder turns saving off (output is still clipped) instead of stopping the server.
- `process read` pages default to `max_inline_output_bytes` instead of 200 KB; keep reading from `next_after`.
- `write` (existing file), `replace_text`, and `multi_edit` return a unified `diff` of the change (LF view, 2 context lines, no file header), capped at `edit_diff_max_bytes` (default 4000, `diff_truncated` when cut, 0 turns it off). Saves a re-read to confirm an edit. Edits over 128000 characters (before plus after) or with NUL bytes return `diff_skipped: "too_large"` or `"binary"` instead, as `difflib` gets very slow on big repetitive files.
- New `edit_checks`: map a file-name glob to an argv run after each `write`, `replace_text`, `multi_edit`, or `apply_patch` of a matching file, with `{path}` replaced by the file's path, e.g. `{"*.py": ["python", "-m", "py_compile", "{path}"]}`. The result carries `check: {"ok": true}` or the failing command, exit code, and up to 4000 bytes of output. The edit is kept either way. `edit_check_timeout_seconds` defaults to 30. Off by default.
- `workspace get` and `set_cwd` return `project_instructions`: the contents of `AGENTS.md` and `CLAUDE.md` in the Git root and the cwd, like CLI agents load them, within `max_project_instruction_bytes` (default 8000) in total; a file past the budget is listed as `{"path", "skipped": "budget"}`. Set `project_instruction_files` to change the names, or to `[]` to turn it off.
- Key rules moved into tool descriptions, since some hosts (Quick) drop the server `instructions`: call `workspace get` first, fan out searches, match batch results by index/label, edit only with `filesystem`, commit through `git run`, and no `&&` in PowerShell 5.1.
- New `default_shell: "auto"`, now the default: `pwsh` when PowerShell 7 is installed, on any OS (on Windows it is also looked for in `Program Files\PowerShell\7` and the Store/winget `WindowsApps` folder, so a host started with an old `PATH` still finds it; only a `pwsh.exe` counts), otherwise `powershell` on Windows and `sh` elsewhere. It is resolved once at startup and the `execute` description names the result. `pwsh` is now started by full path, and its shell commands get `NO_COLOR=1` (unless the caller sets it), so error output has no ANSI colour codes. **Behaviour change:** a config without `default_shell` used to get Windows PowerShell 5.1 and now gets `pwsh` when it is installed. Under `pwsh`, errors are laid out differently (no `At line:1 char:N`), `>` writes UTF-8 instead of UTF-16LE, and arguments to native programs are quoted differently. Set `"default_shell": "powershell"` to keep 5.1. Configs that name a shell keep it.
- With `default_shell: "powershell"`, string commands that mention `curl` or `wget` drop those aliases first, so `curl` runs `curl.exe` instead of `Invoke-WebRequest`; other commands run exactly as written. The prelude shares the command's first line, so error line numbers are unchanged, and is skipped for commands that start (after blank lines and comments) with `using`, `#requires`, `param(` or `[CmdletBinding`, which PowerShell accepts only at the start of a script. Scripts that relied on the alias must call `Invoke-WebRequest` by name.
- A string command that fails on `&&` or `||` (not valid in Windows PowerShell 5.1) gets a `hint` saying to chain with `;` or make separate calls. The `execute` description names the configured `default_shell`.
- **Behaviour change:** kill-on-close now actually works. Since 1.8.0, `job.py` used `wintypes.LPSECURITY_ATTRIBUTES`, which `ctypes.wintypes` does not have, so creating the job always failed and was silently given up. Now everything `execute` and `process` start dies when the server exits, however it exits (taskkill /F, crash, Quick restart): dev servers, and also anything launched to outlive its command (`Start-Process`, `cmd /c start`, GUI apps, a tool that restarts Quick). Set `kill_children_on_exit: false` to keep the old behaviour. A failure to create the job is now reported once on stderr. A new test hard-kills a stand-in server and checks its child dies.
- Non-English output comes back intact: on Windows the server switches its console, which children share, to UTF-8 (code page 65001) at startup and restores it at a clean exit, and children get `PYTHONUTF8=1` (Python 3.7+ UTF-8 mode) unless the config or the call sets it. Before, PowerShell (5.1 and 7) and cmd wrote in the OEM code page (437 on US English: `é` became garbage, `日本` became `??`), and piped Python crashed with `UnicodeEncodeError` on characters outside the ANSI code page (cp1252 on US English). UTF-8 mode is used instead of `PYTHONIOENCODING`, which children inherit and which made a Python program's own `subprocess` pipes decode UTF-8 as cp1252. It also makes `open()` and `subprocess` text pipes default to UTF-8 in Python programs; set `PYTHONUTF8=0` to opt out. Python 2 and 3.6 ignore it. Batch files with non-ASCII text should be saved as UTF-8. `workspace get`'s Git lookup and `search` now decode tool output as UTF-8 instead of the system code page, and `search` shows lines and paths that are not UTF-8 (a cp1252 file, for example) with `�` for the bad bytes instead of empty text. The `git` tool passes `core.quotepath=false`, so non-ASCII paths show as themselves instead of octal escapes.
- QUICK.md: Quick runs tool calls sent in the same turn in parallel, not one per turn as it said. Dependent steps (edit then test, `git add` then `git commit`, two commits) must go in separate turns.
- Fix: a `search` query starting with `-` (`--verbose`, `-1`) failed with ripgrep's "unrecognized flag" and returned nothing; the query is now passed with `-e`.
- A `replace_text` or `multi_edit` that finds no `old_text` now says how to fix it in the `content_mismatch` message, so the agent can retry without re-reading the file: either `new_text` (trimmed, 20+ characters) is already in the file, so the edit may already be applied, or the closest lines, numbered `N<TAB>line` like line-mode `read`. Lines of `old_text` with a letter or digit vote for where it starts when they match a file line with whitespace ignored; at least half must agree, at most 12 lines are shown (each cut to 200 characters), and only the span from the first to the last matching line, so padding `old_text` reveals nothing past it. For `multi_edit` the hint is for the failing edit against the content left by the earlier edits. When `old_text` is found several times but once was expected, the message lists the lines the matches start on (up to 10). Lines of `old_text` found more than 100 times in the file (a lone `end`, say) do not vote.
- A `path_not_found` from `filesystem` `read`, `stat`, `list`, `replace_text`, `multi_edit`, `delete`, `move`, or `copy` now ends with suggestions. When the parent folder exists: up to 3 similar entries, ranked as the same name ignoring case, then the same stem with another extension, then one name containing the other (3+ characters), then a typo in the stem (edit distance 1 for stems of 3-4 characters, 2 for longer ones). When the parent folder is missing: the first missing folder, the nearest existing parent, and similar names there. Only folders and entries that pass the read policy are listed or suggested (never denied or out-of-root paths), and at most 10000 entries of a folder are looked at; candidates are ranked first and policy-checked only until 3 pass. The error code is unchanged.
- **Behaviour change:** `execute` no longer kills a command that is still running at its timeout. It keeps running as a `process` entry (id `exec-…`, listed by `process list`, followed with `process read`/`stop`), and the result returns the output so far (same head/tail clipping and `stdout_path`/`stderr_path`) with `success: false`, `exit_code: null`, `error_type: "backgrounded"`, `process_id`, `next_after` (cursor for `process read` `after`), and a `hint`. A command that ends in time returns the usual result and leaves no process entry. New `execute` argument `kill_on_timeout` (default false) keeps the old behaviour (`error_type: "timeout"`, process tree killed); edit checks and the `git` tool use it, so they stay bounded. When `max_processes` processes are already running, the command is killed at its timeout as before, with a `hint` saying why. **Behaviour change:** with no `timeout`, `execute` now waits `execute_background_after_seconds` (new, default 120) instead of `default_timeout_seconds` (600), which risked host and gateway timeouts; `default_timeout_seconds` still applies to `kill_on_timeout` calls and the long-timeout warning. Internally `execute` now runs through the process manager: stdin `input`, `env`, Job Object adoption and redaction work as before (redaction also runs over the joined output, so a secret split across two reads is still caught), and output is held in the bounded `process_buffer_bytes` buffer, so output beyond it (default 4 MB) drops its oldest part, marked at the start of the stream that lost it (`stdout`, `stderr`, or both, each then `*_truncated`), instead of keeping the head. A backgrounded command's stdin is already closed, so `process write` to it fails with `stdin_closed`. With no `input`, the command gets an empty stdin, as before, not an already-closed pipe (with which `rg` and similar tools searched that pipe instead of the cwd). A command that exits while a process it started still holds its output pipes is kept the same way (`error_type: "backgrounded"`, its `exit_code`, `process_id`, and a `hint`) instead of being dropped with that output lost; with `kill_on_timeout` (or at `max_processes`) what it left running is stopped at the timeout. Both pipes now share one deadline, so the reply no longer comes up to a second late per pipe. `process stop` on an exited entry also stops what it left running: on Windows through a job object per process, which cannot catch a process the command started before joining it, or one started outside the caller's job (as a Microsoft Store Python does). Such an entry is not pruned (by `process_ttl_seconds` or `max_processes`) while something still holds its output, and it counts toward `max_processes` like a running one. `process stop` also ends the per-process job after the process exits, so what a gracefully closed command left running is stopped too. On POSIX, stopping an exited entry that nothing holds sends no signal, since its process group id may already belong to an unrelated group; if what holds the output left the group (`setsid`), a reused group id can, rarely, still be signalled.
- **Breaking result shape:** content `search` results (and each `multi_search` entry) are grouped by file: `results` is `[{"path", "matches": [{"line", "text", "before"?, "after"?}]}]` instead of one `{"path", "line", "text", ...}` object per match, so a file with many hits names its path once. New `match_count` gives the number of matches returned. `max_results` still counts matches, and `truncated`, `engine`, `exit_code`, `applied_excludes`, `error`, path shortening and `files_only` output (`[{"path"}]`) are unchanged. Both the ripgrep and the Python engines return the new shape. Clients that read `results[i]["line"]` or `["text"]` must read `results[i]["matches"]`.
- More forgiving `replace_text` and `multi_edit`: when `old_text` has no exact match in the LF view, the edit retries ignoring typographic variants (curly quotes as straight ones, dash variants as `-`, no-break and other Unicode spaces as a space; each maps to one character), then line by line ignoring trailing whitespace as well (whole lines only). A fallback is used only when it finds exactly `expected_occurrences` matches that do not overlap; otherwise the next tier is tried, and when none fits the edit fails, with each tier's count in the message (`found 0 exact, 2 ignoring typography, 2 ignoring trailing whitespace`) and the lines its matches start on, or the closest-lines hint when no tier matched at all. Exact matches always win, and an edit whose `old_text` or `new_text` holds a lone CR (such as one that changes only line endings) never falls back. The matched spans of the file are replaced, so untouched bytes and line endings stay exact, and the result says how it matched: `"match": "typography"` or `"trailing_whitespace"` (per edit in `multi_edit`); exact matches add nothing. The hint now also ignores typographic variants. Matches are now mapped from the LF view back to the file instead of re-run on the raw text, so in a file with mixed line endings an edit over a minority-ending line no longer rewrites every other line to the dominant ending.
- `filesystem` `read` on a directory lists it, as CLI agents' read tools do, instead of failing with `not_file`: the result is the `list` result (same `limit`, `offset`, `glob`, `include_hidden`, and read policy) plus a `note` that the path was a directory.
- Line-mode `read` with a `line_start` past the end of the file no longer fails with `invalid_arguments`: it returns a `note` (`line_start N is past the end; the file has M lines.`) and the file's last lines (up to 100, numbered `N<TAB>line`, within `max_read_chars`), with `line_start`/`line_end` set to the lines shown and `total_lines`. An empty file gives the note and no lines (`line_start` and `line_end` 0).
- New `batch` argument `sequential` (default false): the calls run one at a time in order and stop at the first failed call (an `error`, or a result with `success: false`, i.e. `execute` and `git`); later calls come back as `{"index", "tool", "label", "skipped": true, "reason"}` without being run, and the reply adds `completed` and `stopped_at`. Once the run has taken longer than `execute_background_after_seconds`, the calls left are skipped as well (their `reason` names the time budget), since one server worker runs the whole batch and the client may have given up. Dependent steps such as edit, run tests, `git commit` now fit in one round-trip and stop before the commit when the tests fail. Other result shapes never stop the run (an edit whose `check` has `ok: false` counts as done). Without it, `batch` runs in parallel with the same reply as before. QUICK.md says dependent steps may go in one sequential batch instead of separate turns.
- **Behaviour change:** an oversized result (over `max_result_bytes`) is easier to read: instead of `{result_too_large, bytes, result_path, hint, preview}` with ~2 KB of raw JSON text in `preview`, the reply keeps the result's own shape and fields (`path`, `content`, a batch's `results` list, ...) with every long string cut to its head, on a line boundary when possible, plus `...[cut: showing lines 1-N of M; full result in result_path]` (or `B of T bytes`). The per-string cut shrinks, and then long lists are cut to their first items plus a marker entry, until the reply fits in `max_result_bytes // 4` (50 KB by default). `result_too_large: true`, `bytes`, `result_path` and `hint` come first and replace same-named result keys (a `hint` of the result's own is kept after the added one). Paths and ids are never cut; cursors that described the uncut value (`next_line`, `next_offset`, `next_after`, `line_end`, `bytes_returned`) are dropped and `truncated` / `<key>_truncated` set to true (where the object has that key; none is added) in every object that holds a cut string or list, directly or nested (the chunk texts of a `process read` with `format: "chunks"`, say), so a cut read is not continued from a cursor that skips lines; the `hint` then names the dropped cursors and says to take them from `result_path` or pass a smaller `limit_bytes` or line range. A string only slightly over the cut stays whole, and a cut snaps to a line end only when that keeps at least half of it. A result that is not an object, or cannot be cut to fit, still gets the raw-JSON `preview`; a failed save still gives `result_path: null`. The full result is saved as before, and the reply never exceeds `max_result_bytes`, which must now be at least 1024 (checked whenever a config is built, not only by `Config.load`); below about 3 KB (depending on the length of `result_path`) the reply is always the raw-JSON `preview`, as a quarter of it cannot hold the added keys plus a cut string.
- **Behaviour change:** argument values are fixed to the schema type before dispatch, also inside `batch` calls, `multi_search` entries and `multi_edit` edits. Before, only argument names were renamed, so a string value was used as it came: `filesystem delete` with `recursive: "false"` ran `rmtree` (a non-empty string is truthy), `glob: "*.py"` became one glob per character (`*` then matched every file, in `search` and `list`), `fixed_string: "false"` still searched literally, and stringified `edits`, `calls`, `searches` or `env` failed. Now `"true"`/`"false"` (any case) become booleans, digit strings integers or numbers, a bare string a one-item list for list-of-string arguments (also a string that is JSON but not a list of strings, such as the character-class glob `[1]`, which used to become `[1]` and crash `search` and `list` with a raw `TypeError`), and a JSON string holding the expected array or object is parsed. Any other string for a boolean, number, array or object fails the call with one `invalid_arguments` error listing every bad argument (`recursive: expected true or false, got 'maybe'; limit: expected an integer, got 'lots'`), as does a non-boolean other than `null` for a boolean (`recursive: 1` used to run `rmtree` too) and a digit string too long for Python's integer parsing (over 4300 digits, which used to be an `internal_error`). In `multi_search`, a bad entry fails only itself: that entry's result has the `invalid_arguments` error and the other searches still run. Values of other types are passed on as before.
- **Behaviour change:** `apply_patch` places hunks by content instead of by line number only, so a diff written with slightly wrong line numbers or counts (as models often write them) still applies. Each hunk's context and removed lines must match exactly: they are tried at the line the header states, then at the nearest line where they match, searching both ways but only after the previous hunk (hunks apply in order and never overlap). Two equally near matches fail with `content_mismatch` naming both lines. Header line counts are no longer checked (they used to fail with `Hunk expects N old lines, found M`); the body decides. A `--- ` line inside a hunk ends it only when a `+++ ` line and then an `@@` hunk header follow, so a removed line starting `-- ` (even followed by an added line starting `++ `) is kept. git header lines (`diff --git`, `index`, `similarity index`, `new file mode`, `deleted file mode`, `old mode`/`new mode`) are skipped instead of failing with `Expected '--- ' header`; a mode-only section changes nothing when the patch has other files too, while a patch with only mode changes fails with `patch contains no files`. A rename or copy (`rename from`/`rename to`, `copy from`/`copy to`, or git `a/` and `b/` paths that differ) is refused with `invalid_arguments` naming both paths: move the file first, then patch the new path. A plain `diff -u x.orig x` still patches `x`. A git binary patch fails with `binary_file`. All-or-nothing writes, line endings and the zero-length insert (`-N,0`) are unchanged; a hunk whose body only adds lines is that insert after line N whatever its header's old count, and one with context or removed lines starts at line N even under a `-N,0` header (so `hunks` no longer reports it as moved when it landed there). Placement runs one string search per hunk over the file, so a hunk in a long run of equal lines (200000, say) no longer takes seconds to place or to fail.
- **Behaviour change:** `filesystem move` no longer replaces an existing destination file silently, and `copy` of a file no longer overwrites one either: both refuse with `invalid_arguments` unless the new argument `overwrite` (default false) is true. An existing destination directory is never replaced or merged, with or without `overwrite` (as `copy` of a directory already did); a file is no longer copied into an existing directory named as the destination (`copy` used to do that) or failed on by `move` with a raw OS error: both now say to give the full destination path. A move onto the source itself is not an overwrite. A folder moved or copied into its own subfolder now fails with `invalid_arguments` up front: `copy` used to recurse about 1000 levels, leave that tree on disk and fail with a raw `RecursionError`, and `move` failed with a misleading `permission_denied`. A file copied onto itself (another spelling or case of its path) fails with `invalid_arguments` too, instead of `already exists` or, with `overwrite`, `permission_denied`. A `move` that changes only the case of a name (`Case.txt` to `case.txt`) on a case-insensitive file system now renames it (directly where the file system allows, as on Windows, otherwise through a temporary name; if that step fails and the file cannot be put back, the error names the temporary path) instead of reporting success and leaving it as it was. On a case-sensitive file system, where `Case.txt` and `case.txt` can be hard links to one file, such a move drops the old name instead of reporting success with both left.
- New `process` action `wait`: blocks until the process exits, a finished output line matches the optional regex `pattern` (new argument), or `wait_ms` passes (default and max 60000), and returns the status plus `reason` (`matched`, `exited`, `timeout`), `matched` (the line or `null`), `tail` (the last `tail_lines` lines, new argument, default 40, max 1000, within `max_inline_output_bytes`) and `next_after`. `pattern` looks at lines that end after `after` (default 0); a line the cursor cuts is matched whole. After a match, `next_after` is the chunk holding the matched line and a `wait` from it goes on with the next line, even in the same chunk (so `Compiled` then `Tests passed` from one write both match). Without a `pattern`, a process that exited while something it started holds its output pipes ends the wait after a one-second grace, with `reason: "exited"` and `output_held: true`, instead of blocking for all of `wait_ms`. With a `pattern`, it keeps watching until `wait_ms` passes, so a line from a daemon a launcher started still matches (`output_held: true` comes with any `reason` once the process exited). Once the process exits, each stream's unfinished last line is matched too, after the finished lines and oldest stream first, once in a chain of `wait`s from each `next_after` (for such a line, `next_after` is the newest chunk, so it never moves back), whatever each `wait` returned, so polling `wait` again after a `timeout`, or a pattern `wait` after one without a pattern, still catches a last line printed without a newline. A `wait` from a cursor that `read` returned goes on after the whole chunk, so it does not repeat lines `read` showed, unfinished last lines included, also in later `wait`s from its `next_after` after one that did not match. Cursors are plain chunk numbers, so two `wait` chains whose `next_after` is the same chunk share what counts as already seen. Saves `read` polling during long builds and test runs.
- **Behaviour change:** each line in line-mode `read` and in `search` results (match `text`, `before`/`after` context, both engines) is cut to 2000 characters, marked `...[line cut: N chars]` with N the line's full length, so one minified line cannot use the whole reply. Line-mode `read` used to show a long line up to `max_read_chars`; the old ` ...[line cut]` marker still ends a line cut by that smaller budget. A ripgrep run past its 60 s timeout used to come back as a raw Python `TimeoutExpired` message; it now fails with code `timeout` and says to narrow the path, add a glob, or exclude big folders.
- **Behaviour change:** a negative `line_start` in line-mode `read` reads from the end of the file (`-50` gives the last 50 lines, at most 2000, numbered with their real line numbers, plus `total_lines`) instead of being silently treated as 1. It cannot be combined with `line_end` (`invalid_arguments`). If `max_read_chars` cannot hold them all, the newest that fit come back with `truncated: true` and a `note`. An empty file gives no lines, with `line_start` and `line_end` 0.
- **Behaviour change:** a UTF-8 byte order mark (BOM) is kept out of the way: `read` (byte mode from offset 0, and line mode) and `workspace` `project_instructions` no longer return it as a `\ufeff` at the start of the text, and `replace_text`, `multi_edit`, `apply_patch` and `write` match and diff without it and write it back on a file that had one. Before, a patch touching line 1 of such a file failed (`expected 'first', found '\ufefffirst'`) and `write` dropped the BOM. A patch made by `git diff` from such a file, which shows the BOM as `\ufeff` on line 1, applies as well: the first old and new line of a hunk at line 1 compare without it. A file that is only a BOM reads as empty (no lines). Like line endings, `write` always keeps an existing file's BOM, whatever the new content starts with (delete the file first to drop it); a file without a BOM gets one only when the new content starts with one, and a new file is written as sent.
- New `replace_all` argument for `replace_text` and each `multi_edit` entry: replaces every exact match of `old_text` without knowing the count; at least one must be found. It cannot be combined with `expected_occurrences` (`invalid_arguments`), and it never uses the typography or trailing-whitespace fallback (a wrong fallback match would be repeated everywhere). The count-mismatch message now mentions it.
- A relative path missing from the runtime cwd that exists from the Git root (copied from `git status` after `set_cwd` into a subfolder) is now used from the Git root by `read`, `stat`, `list` and `search`, with a `note` saying which path was used; write actions are not retried, and their `path_not_found` names the Git-root path instead of similar names; a `write` of such a path fails with `invalid_arguments` naming it instead of creating a second file in the cwd (`./name` creates one there). The same path policy applies. A missing `search` path now also gets the did-you-mean suggestions.
- New `git` argument `include_untracked` (with `action: "diff"`): the diff also shows untracked files that `.gitignore` does not hide, as added. They are added as intent-to-add to a fresh throwaway index (`GIT_INDEX_FILE`) and diffed with the same `args` after the plain diff, which runs against the real index; the real index is never touched. Each new file's part is cut to 8000 bytes so one huge file cannot flood the reply, and the result adds `untracked_files` (the new files the diff shows, counted from its `diff --git` headers, so a pathspec without `--` or a `--diff-filter` is taken into account and output without headers such as `--stat` gives 0; only those under the pathspecs after `--` in `args` are listed, when given). An untracked nested repository and files over `max_file_read_bytes` are left out and listed in `untracked_skipped` (up to 50), so one cannot fail the whole diff or be read whole into memory; if adding the new files still fails, the plain diff comes back with a `note` giving git's error. Working tree only: `--cached`, `--staged`, `--merge-base` or a revision in `args` (`HEAD`, a sha, `a..b`) fails with `invalid_arguments`, since the throwaway index would show every tracked file as deleted. The value of `-S`, `-G`, `-O` or `--diff-filter` may be a separate argument (`-S HEAD` is not a revision); other option values must be attached (`-U1`, `--relative=dir`). Colour output (`--color`, `--color=always`, `--color-words`, `--word-diff=color`) fails with `invalid_arguments` too, as colour codes hide the `diff --git` headers new files are counted and cut at; `--color=never`, `--color=auto`, `--no-color` and a `--no-color` after `--color` are fine (the last `--color`/`--no-color` counts; an option's value such as `-S --color` and a pathspec after `--` are not colour flags, nor `--cached`/`--staged`/`--merge-base` flags), and colour from git config (`color.ui` or `color.diff` set to `always`) is turned off for these diffs. With `--exit-code` or `--quiet` the new files are still added, and `exit_code` is 1 when tracked or new files differ.
- **Behaviour change:** `workspace get`/`set_cwd` read `AGENTS.md`/`CLAUDE.md` from every folder between the Git root and the cwd (so a subfolder's rules apply when working there), not only the Git root and the cwd; with no Git root, from the cwd and its parents up to `workspace_root` (before: the cwd only). Outermost first, deduplicated, within the same `max_project_instruction_bytes` budget and read policy. New config `load_project_instructions` (default true): false turns it off completely, so no instruction file is read and no `project_instructions` comes back. `project_instruction_files` still picks the file names.
- `batch` entries accept tool names other agents use: `bash`, `shell`, `sh`, `powershell`, `pwsh` and `cmd` run as `execute`, `grep`, `rg` and `ripgrep` as `search`; the entry reports the tool that ran and a `note` saying to call it directly (for the shell names, also that a string command runs in the configured `default_shell`, not in the shell named). Top-level names are unchanged (the host checks those).
- A `search` regex that ripgrep rejects but PCRE2 handles (look-around, backreferences; ripgrep's error suggests `--pcre2`) is retried once with `--pcre2`, and the result adds a `note` saying so. If the retry fails too because this ripgrep build has no PCRE2, the first error is returned with a `note` saying PCRE2 is unavailable; a retry that exits 2 only because some files could not be read (locked, denied) or matched (a PCRE2 match limit) is kept, not discarded; only `error compiling pattern` (or a `regex parse error`) counts as a failed retry. The Python fallback engine already supports both.
- `delete` no longer fails with `permission_denied` on read-only files on Windows (a folder holding a Git repository, whose object files are read-only, a read-only file with plain `delete`): it clears the read-only attribute and retries the entry once. Links are never followed or changed: a read-only file with other hard links (as `git clone --local` makes in `.git/objects`) still fails with `permission_denied`, since the attribute is shared by every name. Other systems behave as before.
- `replace_text` and `multi_edit` accept `old_text` copied with line-mode `read`'s `N<TAB>` prefixes, as a last fallback (`"match": "line_numbers"`): every line must have one, the numbers must run on, and the lines must be exactly the file's lines at those numbers. `new_text` loses its prefixes too if every line has one; prefixes on only some of its lines fail with `invalid_arguments`. An `old_text` whose one exact match starts inside a line, or whose numbered reading matches too, is refused as unclear (`content_mismatch` naming both lines); numbered data (a TSV) whose match starts a line edits as before. One expected match only, never with `replace_all`; a prefixed miss gets a hint to leave the prefixes out. In `multi_edit` the numbers are those of a read taken before the call, so an entry whose `old_text` reads as numbered lines reaching a line an earlier entry shifted (from the line where that entry changed the line count, on) is refused, whether it would match exactly or by its numbers (`content_mismatch`, with a hint to put line-numbered edits first, ordered bottom to top, or drop the prefixes) rather than edit a shifted line; numbered lines above every such change apply, unless an earlier entry changed them (they matched the file at the start of the call but no longer do), which is refused too, with a hint to put line-numbered edits first or fold the change into the earlier edit (dropping the prefixes there would only find another copy). An unclear-match refusal does not advise `expected_occurrences`. **Behaviour change:** an empty `old_text` now fails with `invalid_arguments` (it used to insert `new_text` into an empty file, and miss with a confusing count otherwise).
- git never waits for input. Every `git` tool command runs with `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never` and `GIT_EDITOR=true`/`GIT_SEQUENCE_EDITOR=true`, so a credential prompt or an editor (notepad, say) can no longer hang it until the timeout; **behaviour change:** a `commit` without `-m` now fails at once with git's empty-message error, and `merge`/`rebase -i` take the default message and todo. The presets and `include_untracked`'s runs also get `GIT_OPTIONAL_LOCKS=0`, so they do not clash with an IDE over `index.lock`. `execute` and `process` children get `GIT_TERMINAL_PROMPT=0` and `GCM_INTERACTIVE=never` by default. `GIT_ASKPASS` is untouched; a value from the config or the call wins, and denied names are never added.
- `apply_patch` reports like the other edits: each file it changes gets the same `diff` as `replace_text` (same cap and `diff_skipped` rules; not for a file it creates, like `write`), `added`/`removed` line counts, and `hunks: [{"stated", "placed"}]` (1-based old line numbers) for the hunks that landed away from the line their header states, so a wrong placement shows without a re-read. The key is left out when every hunk landed as stated.
- `apply_patch` refuses a patch that names one file in two sections (under any spelling of its path) with `invalid_arguments`: each section was built from the file on disk, so the second write silently dropped the first one's change while both reported it. Merge the hunks into one section.
- `search` spreads a capped page across files: with many matches in a few files, all `max_results` shown used to come from the first file. Now each file keeps at most `max_results` matches, at most 5 times `max_results` are collected in all, and the page takes them round-robin by file (files in their order, matches in line order), with `"spread": true` when several files share it. A cut page adds `total_matches` (exact with ripgrep, whose output was already read whole) or, when the Python engine stopped at the bound, `total_matches_at_least`. `match_count` and `truncated` keep their meaning. The Python engine may now read up to 5 times as many matches before it stops.
- New config `advanced_features` (default false) switches the `batch` and `multi_search` tools and `filesystem` `multi_edit` (with its `edits` argument). Off, they are left out of `tools/list`, the descriptions and the server instructions, and a call to them fails like any unknown tool, action or argument. `replace_text` `replace_all`, `git` `include_untracked` and `process` `wait` stay on either way. **Behaviour change:** a config without the key no longer gets `batch`, `multi_search` and `multi_edit`; set `"advanced_features": true` to keep them. **Warning:** These features can cause Quick agents to have issues: responses often get interrupted for various reasons, and sub-agents especially can get stuck. The cause hasn't been found and it happens often. Use at your own risk.
- An argv command whose program cannot be found (`execute`, `process start`) fails with `command_not_found` (`Program not found: X.`, on Windows with a PATH / `shell: true` hint) instead of a raw OS error.
- An unknown config key fails with a plain `unknown config key: X` (`unknown config keys: X, Y`) instead of Python's own message.
- `SystemDrive` is inherited by default and in `localforge.example.json`, so a child no longer resolves `%SystemDrive%\ProgramData` under its cwd and leaves a `%SystemDrive%` folder in the workspace. A config with its own `inherit_environment` list must add it.
- A `replace_text` or `multi_edit` whose `old_text` is not found at all no longer suggests `expected_occurrences` / `replace_all`; that tip is kept for a wrong count.
- README and QUICK.md are shorter.

## 1.9.2

- The default excludes (`.git`, `.venv`, `__pycache__`, `node_modules`, `.hg`, `target`, `dist`, `build`, `*.egg-info`) now apply at any depth under ripgrep, e.g. `packages/web/node_modules`. ripgrep reads a glob with a slash as anchored to the search root, so they only covered the top level. They are now reported as `**/node_modules/` etc. in `applied_excludes`; the trailing slash makes ripgrep skip those folders instead of walking them, and keeps files with those names.
- The Python search fallback now matches globs like ripgrep `-g` instead of `Path.match`: a glob with a folder is anchored to the search root (`src/*.py` no longer matches `a/src/x.py`), `**` spans any number of folders on every Python version, `{a,b}` alternates (a slash anywhere in the pattern anchors every alternative), matching is case-sensitive on Windows too, a bare-name exclude hides matching folders at any depth, a folder-only include (`src/`) matches no file, an empty glob is ignored, and `[!]x]` is a class. Each verified against ripgrep 15.1.0.
- The Python fallback's glob matching no longer backtracks exponentially on star and `**` chunks: they are matched atomically and runs of `**/` collapse, so patterns like `*a*a*a*a*a*a*a*a*a*a*b` or `**/**/**/…/y` no longer take seconds per path. A few contrived shapes (many negated classes between stars, or repeated `**/*/` on very deep paths) can still be slow. A glob that expands to more than 64 brace alternatives is rejected with `invalid_arguments`.
- Python fallback, more ripgrep parity (each checked live): a folder-only exclude ending in `**` (`src/**/`, `**/`) hides only folders below it and keeps the files beside it; a pattern of slashes alone matches nothing as an include and is ignored as an exclude; a class whose range covers `/` (e.g. `[ -~]`) can match it; `&`, `~`, `|` and `[` in a class are literal, and a doubled `-` no longer raises a FutureWarning; ranges such as `[+--]` and `[--0]` keep their meaning. Like ripgrep, a range followed by `-X` has its end replaced by X (`[a-c-e]` is a to e, `[a-c-b]` is a to b), and a reversed step is rejected as an invalid range (`[a-b--c]`, `[b-a-c]`).
- A single-file search with the Python fallback reads only that file, and ignores excludes like ripgrep does for an explicit path; it used to also search same-named files in subfolders.

## 1.9.1

- `search` globs with a folder (e.g. `src/*.py`, `src/**/*.cs`) now match with ripgrep. ripgrep matches such globs against the path relative to its working directory, and it ran from the server's directory instead of the search root, so they silently returned nothing. Include and exclude globs (including the built-in excludes such as `node_modules/**`) are now relative to the search `path`; before, ripgrep ignored excludes unless the server happened to run from the search root.
- `search` `truncated` is true only when results were actually cut, not whenever the result count equals `max_results`.

## 1.9.0

- Breaking response shapes: line-mode `read` returns `content` instead of `lines` and omits `total_lines` when truncated; search context returns `before`/`after` instead of `context`; `process read` returns `stdout`/`stderr` instead of `chunks` unless `format: "chunks"`; `structuredContent` is opt-in. Clients that parse the old fields must update.
- Edits keep line endings: `write` (existing file), `replace_text`, `multi_edit`, and `apply_patch` preserve the file's dominant line ending instead of converting LF files to CRLF on Windows. New files, and files with no line break yet, are written exactly as sent. Detection runs on decoded text, so `write`, `replace_text`, and `multi_edit` work on UTF-16 files (line-mode `read` and `apply_patch` still reject them as binary). `write` reports the kept ending as `eol`; delete the file first to change it. `old_text`/`new_text` copied from a CRLF byte read still match. `replace_text` and `multi_edit` count matches in the LF view the agent reads and leave untouched lines byte-exact (mixed endings, stray CRs) when that gives the same change; otherwise the edit is applied to normalized text. `apply_patch` keeps each untouched line's ending, splits lines on LF only (a form feed no longer breaks a patch), and adds a line break when lines are added after a last line that had none. A zero-context insert hunk (`@@ -N,0 ... @@`) now inserts after line N instead of before it; one past the end of the file is rejected. Reported `bytes` are now the bytes actually written.
- `execute`, `git`, and `process start` resolve a missing or relative `cwd` against the runtime cwd (`set_cwd`). `process start` used to run in the workspace root.
- Line-mode `read` reads in bounded pieces (no whole-file load, no `max_file_read_bytes` limit, over-long lines skipped without loading) and returns numbered text in `content` (one `N<TAB>line` per line) instead of a `lines` array of objects. Output stops at 2000 lines or `max_read_chars` (default 60000, minimum 64) instead of scanning to the end; `next_line` says where to continue, and `total_lines` appears only when the read reaches the end of the file. Only LF ends a line, as in ripgrep. Over-long lines are cut.
- Search context comes back as `before`/`after` lists of `N<TAB>line` instead of one unlabeled `context` list, and ripgrep context no longer bleeds across file boundaries. Both search engines include neighboring match lines in context and split lines on LF only, so they return the same context and line numbers. Result paths under the runtime cwd are relative to it.
- `execute` output over `max_capture_bytes` keeps the head and the tail (where build and test errors usually are) with a cut marker, instead of the head only.
- `process read` returns `stdout`/`stderr` strings by default; `format: "chunks"` keeps the previous per-chunk shape.
- Tool results use compact JSON. `structuredContent` is opt-in (`structured_content: true`): Quick showed both copies on failed calls.

## 1.8.0

- Durability hardening for long-running sessions:
  - `process write` and stdio responses now write on a helper thread with a 30s timeout (new `stdin_blocked` code); a child that never drains stdin, or a host that stops reading stdout, can no longer pin a worker thread forever.
  - Pending stdio requests are bounded at 128: a request flood gets an immediate per-request error (`-32603`) instead of unbounded memory growth, and a clean EOF no longer waits on an unbounded backlog.
  - Children are adopted into a Windows Job Object with kill-on-close (via `ctypes`, no dependencies): they die with the server however it exits — taskkill, crash, host restart after hibernation — not just on clean exit. Grandchildren join the job automatically. Set `kill_children_on_exit: false` to opt out. Off Windows, adoption is a no-op.
  - `process read` waits on a condition variable instead of polling at 20 Hz; idle waits cost no CPU.
  - Once stdout is stuck or broken, the server stops writing for good instead of silently failing every subsequent response.
